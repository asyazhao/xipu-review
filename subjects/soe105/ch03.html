程序开发过程与过程抽象

Program Development & Procedural Abstraction

来源 L02 · 术语 10 个

本讲把“写程序”拆成可重复的五个阶段，并用一个美元硬币兑换人民币的例子走完全程：从问题识别、分析、算法精化，到用过程抽象把子问题交给函数，最后进入实现与测试。

本章要点

  • 程序开发过程分五阶段：问题识别、问题分析、算法设计、实现、调试与测试。
  • 问题分析要明确输入、输出、约束与所需的抽象（数据类型）。
  • 算法设计包括分解、初始算法与算法精化三步；分解会产生新的中间变量。
  • 过程抽象是把某个子问题暂时搁置、只保留接口，稍后再解决。
  • C++ 程序由注释、预处理指令、函数与语句构成，main() 是程序起点。
  • 四类错误：语法错误、链接错误、运行时错误、算法错误。
  • 调试应自顶向下进行，重点关注各主要步骤/函数之间的接口。
  • 过程抽象支持自顶向下设计、信息隐藏与代码复用。

3.1 程序开发过程的五个阶段

讲义把开发过程分为五步：

  1. 问题识别（problem identification）：这个问题到底在讲什么？题面有没有歧义？
  2. 问题分析（problem analysis）：输入是什么、缺什么、怎么得到；输出要求什么；在什么约束下；需要哪些抽象、哪些数据类型。
  3. 算法设计（algorithm design）：分解、初始算法、算法精化。
  4. 程序实现（implementation）：用编程语言把算法翻译成程序。
  5. 调试与测试（debugging, validation and testing）。

流程图把前三个阶段归为“问题求解阶段”（problem-solving phase），后两个阶段（含翻译与桌面测试 desktop testing）归为“实现阶段”（implementation phase），终点是“可运行的程序”。桌面测试指不上机、用纸笔手工跟踪算法，它是实现阶段的第一步，而不是最后一步。

考点

五阶段的顺序与归属：问题识别、问题分析、算法设计属于问题求解阶段；翻译、桌面测试、测试属于实现阶段。

3.2 问题识别与问题分析：硬币兑换的例子

讲义用一个具体题目贯穿全讲：给定一堆 5 美分硬币（nickels）与 1 美分硬币（pennies），求兑换得到多少元人民币与多少枚 1 角硬币。

问题识别阶段只问一件事：题面有歧义吗？“兑换”的汇率没有给出，这是必须补上的信息；此外“元”与“角”的关系也需要明确。问题分析阶段把答案写成三类：

  • 输入：nickels（5 美分硬币枚数，整数）、pennies（1 美分硬币枚数，整数）；
  • 输出：yuans（兑换得到的人民币元数，整数）、change（1 角硬币枚数，整数）；
  • 约束：本题无特殊约束（None）。

讲义还要求回答“需要哪些抽象、哪些数据类型”。这里的选择是：枚数与元、角用整型，中间出现的总金额用实型（real），因为汇率换算会产生小数。

易错

“输入是什么”不等于“题面第一句给了什么”。输入要写成带名字、带类型、带单位的量，例如“nickels —— 5 美分硬币的枚数 —— 整数”，否则后面的算法没有可操作的对象。

L02 p.8–9

3.3 算法设计：分解与中间变量

算法设计的第一步是分解decomposition：把大问题切成更小的子问题。讲义把兑换问题切成三块，并明确每块的输入与输出：

  1. 求美元总额：输入 nickels、pennies，输出 total_US_dollars；
  2. 求兑换后的人民币总额：输入 total_US_dollars，输出 total_chinese_yuans；
  3. 求元数与角数：输入 total_chinese_yuans，输出 yuans 与 change。

每一块的输出都成为下一块的输入，于是产生了两个新的中间变量intermediate variable：total_US_dollars（美元总额，实型）与 total_chinese_yuans（人民币总额，实型）。讲义的数据流图把这条链画得很清楚：nickels、pennies → 计算美元 → total_US_dollars → 兑换 → total_chinese_yuans → 拆分 → yuans、change。

这张图正是算法设计的产物：它先于任何一行代码存在，却已经决定了程序的结构——三个处理块、两个中间变量、两个最终输出。

L02 p.10–11

3.4 算法精化：从步骤到公式

初始算法只有五句自然语言：读入硬币枚数；计算美元总额；计算兑换后的人民币总额；求出元与角；输出结果。这样的粒度还不能直接编码，需要算法精化algorithm refinement，把每一步落到可计算的表达式。

讲义给出的精化过程，先把每一步写成可计算的表达式（已知 1 美元 = 100 美分，常量 DOLLAR2CENTS = 100）：

  • total_US_cents = 5 × nickels + pennies，再换算为美元 total_US_dollars = total_US_cents / DOLLAR2CENTS
  • total_chinese_yuans = exchange_us2yuan(total_US_dollars)
  • total_chinese_cents = total_chinese_yuans × DOLLAR2CENTS
  • yuans = total_chinese_cents / DOLLAR2CENTS
  • change = total_chinese_cents % DOLLAR2CENTS / 10

最后一行是整数运算的典型写法：先用取模得到不足 1 元的部分（美分），再除以 10 换成 1 角硬币的枚数。这里依赖 C/C++ 的整数除法会截断小数这一性质，若把中间量写成实型，结果就会带上小数，反而要额外取整。

易错

单位换算方向：美分换美元要除以 100。讲义示例代码中把该行写成乘 DOLLAR2CENTS，与“1 美元 = 100 美分”的方向相反，属笔误；理解与答题时以单位换算关系为准。

L02 p.12–13, p.23

3.5 过程抽象：把子问题交给函数

精化到“计算人民币总额”这一步时，讲义没有继续展开，而是造了一个函数：exchange_us2yuan()，输入 US_dollars（美元金额），输出 chinese_yuans（兑换后的人民币金额）。这一步被称为过程抽象procedural abstraction：把某个子问题暂时抽象掉，留到后面再解决。

讲义的原话是“此时把这个子问题暂时放到一边”（we temporarily put aside this problem），继续推进主问题的解法。于是算法精化第二版只需写一行：调用 exchange_us2yuan()。主程序与函数之间只剩下一个接口：一个实型参数进，一个实型结果出。

这样做的前提是接口先定下来。只要“输入美元、输出人民币”这个约定不变，函数内部怎么实现都不影响主程序；实现可以晚一点写，甚至可以换人写。

讲义在这里加了一句全讲最重要的提醒：在实现之前，先检查和调试算法（Before implementation, CHECK and DEBUG the algorithm）。接口定得对不对、单位一致不一致，都要在纸上先过一遍。

考点

过程抽象的判定标准是“接口已定、实现暂缺”：函数名、参数与返回值的约定先写出来，函数体可以之后再补。

3.6 C++ 程序骨架

讲义给出 C++ 程序的基本形式：注释、库引用（#include）、预处理语句、函数。main() 这个函数名表示程序的起点，函数名前的返回类型表示执行结束后的返回类型，末尾的 return 0 结束 main()，也就结束了程序。

// helloworld.cpp
#include <iostream>
using namespace std;

int main() {
    cout << "Hello world" << endl;
    return 0;
}

兑换程序的骨架则先摆出声明部分：一个函数声明（float exchange_us2yuan(float);）、若干变量（nickels、pennies、dollars、change 为整型，total_US_dollars、total_chinese_yuans 为实型），以及一个常量 DOLLAR2CENTS。函数声明只写返回类型、名字与参数类型，不写函数体——这正是 3.5 节所说的“接口先定”。

// FILE: excoin.cpp
// DETERMINES THE NUMBER OF CHINESE COINS
// IN EXCHANGE OF US COINS
#include <iostream>
using namespace std;

void main() {
    // function that returns the equivalent
    // Chinese yuan for US dollars
    float exchange_us2yuan(float);

    const int DOLLAR2CENTS = 100;
    int nickels;                 // count of nickels
    int pennies;                 // count of pennies
    int dollars;                 // value of coins in Chinese yuan
    int change;                  // value of coins in Chinese 10-cents
    float total_US_dollars;      // total US dollars
    float total_chinese_yuans;   // total Chinese dollars
}

讲义提醒：此刻不必看懂每一行；而且这份源码还不能编译，因为 exchange_us2yuan(float) 的定义仍然缺失。缺失的定义会在后续讲次补上。

易错

函数声明（declaration）与函数定义（definition）不同：声明只给编译器一个签名，定义才提供函数体。只声明不定义，程序能通过编译，却会在链接阶段失败。

3.7 调试与测试：四类错误

实现之后要编译、运行，并用不同且随机的输入测试。讲义把错误来源分成四类，对应程序生命周期中的不同阶段：

  • 语法错误syntax error：程序无法编译。多因编码粗心，相对容易修。
  • 链接错误link error：程序无法链接。多因忘记引入库或用错语言库。
  • 运行时错误runtime error：程序能编译能链接，但结果不对，属实现（编码）错误，需要定位 bug 并修复。
  • 算法错误（algorithmic error）：算法本身错了。若在实现前认真检查并证明过算法，这类错误本不该出现。

调试的原则是自顶向下（top-down），并特别关注主要步骤/函数之间的接口：input → nickels、pennies；nickels、pennies → total_US_dollars；total_US_dollars → total_chinese_yuans；total_chinese_yuans → yuans、change；yuans、change → output。接口处的单位、类型、取值范围最容易出错。

讲义给出两组测试：输入 34 与 107，输出“19 元 7 角”；输入 20 与 22，输出“8 元 6 角”。测试数据要覆盖边界与随机值，而不只是刚好能跑通的那一组。

考点

四类错误的分期：语法错误在编译期、链接错误在链接期、运行时错误在运行期、算法错误在设计期。算法错误不能靠调试器发现，只能靠事先的检查与证明。

L02 p.25–26

3.8 为什么需要过程抽象

讲义从三个角度论证过程抽象的价值。

第一，它支持自顶向下设计：可以把问题分解成更小的子问题（divide-and-conquer），子问题比原问题简单；当子问题只是“同一个问题但规模更小”时，就自然引出递归（recursion），这是一种很强的求解技术；子问题还可以分开解决——不同时间、不同人来做。

第二，对复杂子问题，它提供信息隐藏（information hiding）：把与主问题无关的细节藏起来，主程序因此易读、易改；整个模块/函数可以被替换，而不影响主程序代码。

第三，对频繁出现的子问题，它允许代码复用（code reuse）：只写一次，只有一处需要修改。

把这三点合起来看，过程抽象不是“把代码拆小”的排版技巧，而是控制复杂度的主要手段：人一次只能处理有限的信息，抽象把暂时不需要的信息挡在外面。

辨析

分解（decomposition）是“把问题切成子问题”的动作；过程抽象是“把子问题封装成有接口的函数、暂时不写实现”的决定。前者是设计方法，后者是封装手段。
