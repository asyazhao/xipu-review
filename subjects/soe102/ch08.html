Java I/O：流与文件

Java Input & Output: Streams & Files

来源 W10 · 术语 9 个

虚线下划线为术语；悬停查看中文、英文与释义，完整词典见“术语”。

本讲解决“程序如何与外界交换数据”：用流模型统一文件、键盘与网络，区分字节流与字符流，用包装流加缓冲，用 try-with-resources 保证关闭，再用 NIO.2 的 Path 与 Files 写出更短的代码。

本章要点

  • I/O 是 JVM 与外界的桥：磁盘、控制台、网络，统一抽象为有序的数据流。
  • new File(...) 只保存路径，不打开也不创建文件；相对路径按启动目录解析。
  • 字节流处理原始 8 位数据，字符流处理 Unicode 文本；选错会出现乱码。
  • 包装流不改变接口，只增加行为：BufferedInputStream 仍是 InputStream。
  • read() 返回 0–255 或 −1（EOF）；readLine() 返回一行或 null；write 默认覆盖文件。
  • try-with-resources 在每条路径上关闭资源，多个资源逆序关闭，关最外层即可。
  • Path 是地址，Files 是工具箱；小文件用一行式读写，大文件用缓冲流逐行处理。
  • 文本一律显式指定 UTF-8；序列化只要求能读代码，新系统优先 JSON/CSV。

8.1 程序是一座孤岛：流模型

到目前为止，所有数据都活在内存里：int score = 82;、String name = "Ada";、一个 ArrayList。程序一退出，这些全部消失。文件则能活过进程——Files.writeString(Path.of("scores.txt"), "82"); 写下的内容明天还在。讲义把 I/O 定义为“通往 JVM 之外一切的桥”，并列出三条通道：磁盘（文件与文件夹：配置、数据、报告、图片）、控制台（键盘 System.in 与终端 System.out）、网络（套接字、HTTP，其字节与文件一模一样）。

统一它们的比喻是流stream：一段有序的数据，流入（input）或流出（output）。文件、键盘、网络套接字都用同一套方法读写——“学一次模型，到处适用”。这句话是本章的总纲：后面出现的几十个类，都只是这条模型的不同实现。

辨析

“流”是数据的方向与顺序，不是文件本身。同一个文件可以先被字节流读、再被字符流读；流关掉之后文件还在，流只是当时的通道。

8.2 File 与路径：名字不是文件

File f = new File("data/scores.txt");

f.exists();          // false 表示该路径下什么都没有
f.isFile();          // 是文件还是目录
f.length();          // 字节数
f.getName();         // "scores.txt"
f.getAbsolutePath();
f.mkdir();           // 创建“目录”
f.delete();

最关键的一句：new File(...) 不会打开也不会创建文件，它只持有一个路径字符串，文件可能根本不存在。这是初学者最常踩的坑——以为构造了一个 File 对象就得到了文件。

路径分相对与绝对。"data/scores.txt" 相对于工作目录（启动 java 的地方）解析；绝对路径从根开始，例如 /Users/... 或 C:\\...。讲义特别警告：从 IDE 运行与从终端运行，工作目录可能不同，同一个相对路径会指到不同文件夹。

java.io.File 是 Java 1.0 留下的遗留 APIlegacy API。新代码更愿意用 Path + Files（8.8 节），但旧代码里仍会看到 File。

易错

new File("x.txt") 之后文件并不存在；要真正创建，得调用 createNewFile()、打开一个输出流，或使用 Files.writeString。另外 mkdir() 建的是目录，不是文件。

W10 slide 4

8.3 四个家族：字节流与字符流

Java I/O 的类可以归成两大家族。字节流byte stream处理原始 8 位数据（0 到 255）：基类是 InputStream / OutputStream，常见实现有 FileInputStream、FileOutputStream、BufferedInputStream、BufferedOutputStream、ObjectInputStream、ObjectOutputStream。字符流character stream处理 Unicode 文本：基类是 Reader / Writer，常见实现有 FileReader、FileWriter、BufferedReader、BufferedWriter、InputStreamReader、PrintWriter。

字节流与字符流的分工
维度字节流字符流
基类InputStream / OutputStreamReader / Writer
数据单位8 位字节（0–255）Unicode 字符
适用对象图片、.class、zip、pdf、任意二进制按词读取的文本
典型类FileInputStream、BufferedOutputStreamFileReader、BufferedReader、PrintWriter

为什么需要两套？一个字节是 8 位，一个字符是 Unicode 符号，在 UTF-8 里常常占 2 到 4 字节。字符流会用字符集把字节解码成字符；跳过这一步直接按字节读文本，得到的就是乱码mojibake。判断口诀很简单：读的是“词”就用 Reader / Writer（或 Files），读的是“原始字节”就用 InputStream / OutputStream。

考点

看到图片、音频、zip、序列化对象，选字节流；看到 .txt、.csv、.json 这类文本，选字符流或 Files。选错的典型症状是乱码或文件损坏。

W10 slide 5

8.4 装饰器：包装流与缓冲

裸流很慢：每读一个字节就发起一次系统调用。解决办法是把它包起来，加上内存缓冲：

InputStream raw = new FileInputStream("big.txt");   // 一次一字节，慢
InputStream in = new BufferedInputStream(raw);      // 加上缓冲，同一类型

int b;
while ((b = in.read()) != -1) {
    // 快：大多数读取命中缓冲区
}

这就是装饰器decorator思路：BufferedInputStream 本身就是一个 InputStream，调用 read() 的代码一行都不用改，缓冲被透明地加上去。为什么快？它一次从磁盘取一大块（约 8 KB），之后从内存里逐个发字节——一次 OS 调用替代了成千上万次。

包装可以叠加，每一层只加一种能力。new BufferedReader(new InputStreamReader(in, UTF_8)) 就是“字节 → 字符（指定编码）→ 缓冲”三层。讲义的比喻是：裸管道一次滴一滴，带缓冲的管道有一个蓄水池；包装从不改变“流什么”，只改变“怎么流”。

考点

包装之后类型不变（BufferedInputStream is an InputStream），所以可以赋给父类型变量；关闭最外层即可关闭整条链，不必逐层 close。

W10 slide 6

8.5 读写字节：InputStream 与 OutputStream

try (InputStream in = new FileInputStream("data.txt")) {
    int b;
    while ((b = in.read()) != -1) {
        System.out.print(b + " ");
    }
} catch (IOException e) {
    System.err.println("missing file");
}

read() 返回 int 而不是 byte：正常值 0 到 255，文件结束时返回 −1。为什么用 int？因为 −1 必须在 0 到 255 之外，byte 的取值范围装不下这个“额外的哨兵值”。一个内容为 “Hi!” 的文本文件，这段程序打印 72 105 33——原始字节值，而不是字母。想看到字符就得换 Reader。

写字节用 OutputStream。write(int) 只取低 8 位，所以 write(72) 存下的正是字母 H；也可以传字节数组：out.write("Hi".getBytes());。三个行为要记住：打开已存在的文件默认会清空它；给构造器传 true 才是追加（new FileOutputStream("log.bin", true)）；目标文件不存在会自动创建，但父文件夹不存在会抛 FileNotFoundException。最后，close() 会把缓冲区里的字节刷到磁盘——“关闭即刷新”。

讲义用一句对称性总结：每个输入家族都有对应的输出孪生类，能用 X 读就能用对应的 X 输出类写。

易错

read() 返回 int 且 EOF 为 −1；若把返回值直接当 byte 用，−1 会与合法的 255 混淆。write(int) 只写低 8 位，传超过 255 的数不会报错，只会静默截断。

8.6 文本：Reader、Writer、BufferedReader、PrintWriter 与 Scanner

字符流的 read() 返回字符的码点（int），EOF 仍是 −1；因为返回的是码点，打印前要转成字符：System.out.print((char) ch);。一次读一个字符仍然慢，于是有了 BufferedReader：

try (BufferedReader br =
         new BufferedReader(new FileReader("names.txt"))) {
    String line;
    while ((line = br.readLine()) != null) {
        System.out.println(line);
    }
} catch (IOException e) { ... }

注意这里的结束标记换了：readLine() 返回下一行（不含换行符），文件结束时返回 null，不是 −1。它在底层一次填满约 8 KB 的缓冲，再从内存里逐行发出，通常快 10 到 100 倍。写文本用 BufferedWriter，newLine() 会按平台输出换行。

PrintWriter 把 Writer 包装成你熟悉的 print / println / printf 接口，写文件与写 System.out 的代码看起来完全一样，还支持 %d、%f（%.2f）、%s、%n 等格式。它有两个特点：写入时吞掉 IOException，不会抛出，所以关键写入之后要检查 pw.checkError()；它适合人类阅读的报告与日志，如果数据要被别的程序解析，用 BufferedWriter 更稳。

从控制台读则用 Scanner：System.in 本身只是一个连着键盘的 InputStream，Scanner 在它上面加了各种解析方法（nextInt、nextDouble、nextLine、nextBoolean）。它也能直接读文件：new Scanner(Path.of("a.txt"))，默认以空白分隔。讲义提醒了一个经典陷阱：nextInt() 把回车留在缓冲区里，紧接着的 nextLine() 会读到空串；修法是先多调用一次 nextLine() 把回车排掉。

考点

三种“结束”不要混：字节流 read() 返回 −1；字符流 read() 返回 −1；readLine() 返回 null。Scanner 的 nextInt 后接 nextLine 会读到空行，必须先排掉换行。

W10 slide 9–12

8.7 关闭资源与覆盖/追加

每个流都是资源，必须关闭。AutoCloseable 正是让对象能出现在 try (...) 里的接口：

// 首选：try-with-resources
try (var br = new BufferedReader(new FileReader("a.txt"))) {
    return br.readLine();
}   // close() 自动执行

// 旧写法：finally（要能读懂）
BufferedReader br = new BufferedReader(new FileReader("a.txt"));
try { ... } finally { br.close(); }

四条要点：close() 在正常结束与抛出异常时都会调用，不会泄漏文件句柄；两个资源时后声明的先关（内层包装先于外层文件）；关闭最外层包装就够了，它会一路关下去；忘记关闭的后果是句柄泄漏，缓冲的写入还可能永远到不了磁盘。

讲义用一道“运行两次”的题说明覆盖行为：程序用 new FileOutputStream("log.txt") 写入 'A' 和 'B'，连续运行两次，文件内容两次都是 "AB"——构造器每次都截断文件，数据不会累积。想累积就要显式追加：new FileOutputStream("log.txt", true)，此时第一次 AB、第二次 ABAB。这条规则对 FileWriter、FileOutputStream 与 NIO 的 OpenOption 都成立：默认替换，追加要显式声明。

易错

“写进去了但文件是空的”几乎总是没关闭或没 flush；缓冲区里的数据在 close/flush 之前不会落盘。反过来，“旧内容不见了”几乎总是忘了 APPEND。

W10 slide 13–14

8.8 NIO.2：Path 与 Files

Java 7 起用 Path 取代 File 来表示路径：它不可变，被强大的 Files 类使用。Path.of("data", "scores.txt") 用多个段构造路径，Java 会自动插入正确的分隔符——macOS/Linux 用 /、Windows 用 \，不必手拼字符串。

Path p1 = Path.of("data/scores.txt");
Path p2 = Path.of("data", "scores.txt");

p1.getFileName();              // scores.txt
p1.getParent();                // data
p1.toAbsolutePath();
p1.resolve("a.txt");           // data/a.txt
File old = p1.toFile();        // 桥接旧 API

讲义给了一个好记的比喻：Path 是地址（一个像字符串的对象），Files 是工具箱（在该地址上真正读、写、创建、删除的静态方法）。小文件用一行式：

Path p = Path.of("data.json");

String text = Files.readString(p);          // 读成一个 String
List<String> lines = Files.readAllLines(p);
byte[] raw = Files.readAllBytes(p);         // 二进制

Files.writeString(p, "hello");
Files.write(p, raw);

这些方法都会抛 IOException，并且把整个文件读进内存：几 MB 以内很舒服，巨大的日志就该改用 BufferedReader 或流式处理。讲义给的规则是：小文件用 Files 一行式，大文件或逐行处理用流。

文件管理也是 Files 的活：createDirectories 会建出路径上所有缺失的文件夹，createDirectory 只建一层、父目录缺失就失败；copy / move 接受 REPLACE_EXISTING、COPY_ATTRIBUTES、ATOMIC_MOVE 等可选参数；delete 在文件不存在时抛 NoSuchFileException，deleteIfExists 则返回 boolean。与旧的 File 方法不同，这些操作失败时会抛异常并说明原因，而不是悄悄返回 false。

考点

Path 是地址、Files 是操作；Path.of("a","b") 自动处理分隔符；readString/writeString 默认 UTF-8 且会自动开关流；大文件不能用 readAllBytes。

8.9 目录遍历、打开选项、编码与序列化

Files.list 只列出直接子项，Files.walk 深度优先遍历整棵树。两者都返回惰性的 Stream，背后握着一个打开的目录句柄，所以必须放进 try (...)：

try (Stream<Path> s = Files.list(Path.of("src"))) {
    s.filter(Files::isRegularFile).forEach(System.out::println);
}

try (Stream<Path> s = Files.walk(Path.of("project"))) {
    s.filter(p -> p.toString().endsWith(".java"))
     .forEach(System.out::println);
}

写文件时如何打开，由 StandardOpenOption 决定，常用的四个是：CREATE（不存在就创建，写入的默认值）、CREATE_NEW（只在不存在时创建，否则失败）、APPEND（写在末尾、保留旧字节）、TRUNCATE_EXISTING（打开即清空，写入的默认行为）。不带参数时等价于 CREATE + TRUNCATE_EXISTING + WRITE；要追加必须显式写出来。

编码问题在中文环境里尤其致命。字符是人打出来的，字节是磁盘上的：UTF-8 下 A 占 1 字节，而“中”占 3 字节，A B 中 编码后是 65 66 E4 B8 AD。把 UTF-8 字节按 GBK 解码（或反过来），中文就变成问号或奇怪的重音字母——字节没坏，是解码器错了。因此 new FileReader("cn.txt") 有风险，应写成 new FileReader(p, StandardCharsets.UTF_8)，或直接用 Files.newBufferedReader(p, StandardCharsets.UTF_8)、Files.readString(p, StandardCharsets.UTF_8)。标准建议只有一句：文本文件一律按 UTF-8 读写。

最后是序列化serialization：让类 implements Serializable（一个没有方法的标记接口，等于授权 JVM 把对象字段转成字节），声明 serialVersionUID，再用 ObjectOutputStream 的 writeObject 写出、ObjectInputStream 的 readObject 读回（返回 Object，需要强转）。被引用的对象也会一起序列化，它们同样必须可序列化或被标记为 transient。讲义的态度是：必须能读懂序列化代码，但新系统应避免使用——它对类结构变化很脆弱、其他语言读不了，readObject 还有已知的安全风险；优先用 JSON、CSV 这类文本格式，显式写出字段。

辨析

Files.list 只看一层，Files.walk 递归所有层；两者都必须关闭。readString 适合小文件，walk 适合批量处理——它们解决的是不同规模的问题。

8.10 IOException 处理与六个常见坑

IOException 是 checked 异常，必须有意处理。讲义的原则与异常那一讲一致：先捕获更具体的类型，再兜底父类；在边界处翻译异常；绝不空 catch。

try {
    String t = Files.readString(Path.of(args[0]));
    System.out.println(t);
} catch (NoSuchFileException e) {
    System.err.println("no such file: " + args[0]);
} catch (IOException e) {
    throw new UncheckedIOException(e);   // 在边界翻译
}

底层方法声明 throws IOException 让异常向上传，main 再决定是给用户一句友好提示、重试，还是退出。空 catch 会把“文件缺失”和“数据损坏”一起藏起来，至少也要记录一句。

讲义最后列出六个“评分者最讨厌”的 I/O bug：

  1. 从不关闭流——句柄泄漏，缓冲写入可能永远不到磁盘。一律用 try-with-resources。
  2. 静默覆盖——打开已存在的路径却没有 APPEND，旧内容被清空。
  3. 假设工作目录——相对路径按启动位置解析，IDE 与终端不一样。
  4. 整个大文件读进内存——对 2 GB 日志用 readAllBytes/readString 会 OutOfMemoryError，应逐行流式处理。
  5. 忽略字符集——默认 FileReader 跨机器就乱码，固定用 UTF-8。
  6. 以为 new File("x.txt") 会创建文件——它只持有一个名字。

还有一个与刷新有关的实验：只 new PrintWriter(new FileWriter("a.txt")) 然后 println 一行、不 close 就退出，文件往往是空的——内容还在 writer 的缓冲区里。链条是：write 填缓冲 → flush 推到操作系统 → close 刷新并释放句柄；一个 try-with-resources 把三件事都做了。所以“文件里没有刚写的数据”时，先查 close/flush，再查逻辑。

课堂练习是 LogAnalyzer：用 BufferedReader 逐行读 access.log，跳过空行，统计总请求数与各状态码数量（Map<Integer, Long>），再用 PrintWriter 打印并写入 report.txt；日志缺失时给友好提示而不是抛栈。参考解法的要点是 Files.newBufferedReader 一步拿到缓冲读取器、line.split("\\s+") 按空白切分后取第 5 个字段作状态码、merge(st, 1L, Long::sum) 计数，以及两个 try-with-resources 分别管读与写。

考点

catch 顺序必须是 NoSuchFileException 在 IOException 之前；readString 只适合小文件；PrintWriter 会吞异常，要用 checkError()；数据没落盘先想 close/flush。
